# 从大目录到可执行建议

本次清理暴露的经验是“按具体内容和依赖判断”，不是把本机路径写成永远安全的白名单。下面是调查路线，不是无需核验的删除规则。

| 场景 | 必查证据 | 应给用户的结论 |
|---|---|---|
| `.npm/_npx/<hash>` | 根 package.json 的 dependencies；node_modules 对应包的 name/version/description；具体目录大小；进程/占用 | 按工具、版本、用途列清单。重复版本可作候选，不以新旧判定无依赖；coze-bridge 等可能是仍运行的服务，不是普通下载缓存。移除后再用要下载，可能改变未锁版本。 |
| `.cache` | 下一层与混合子层；运行时/模型的文件名、依赖用途 | Codex runtime、包管理器、自建运行环境不因在 cache 就可删；Hugging Face 模型按 repo/model 名说明用途、体量、离线影响。模型没用才让用户判断删除。 |
| `.codex`、Agent 数据 | 文件/目录大小，数据库、会话、生成图、插件、启动脚本的引用 | 会话/归档/记忆不是纯缓存；归档不等于丢弃。数据库尤其 WAL/SHM 不单删。生成图可挑选但可能影响历史展示。运行环境是否被服务引用要核实。 |
| 已卸载 App | 用户确认 + 已知安装路径；updater 里的 ZIP/版本/日期；残留进程；应用资料独立检查 | 更新包与用户数据分开报。崩溃上报器/桥接 daemon 可在 App 删除后继续运行，不能把没有主 App 当已停止。 |
| Claude/其他虚拟机 | `.img/.vhdx` 文件实占与逻辑容量、压缩镜像、session disk、lsof | 区分 CLI、桌面功能、VM 各自依赖。不能承诺删 VM 后所有桌面功能正常；重新下载会吃回空间。只陈述已验证行为。 |
| 聊天应用容器 | Profiles/App Support 下分层；DB/日志/媒体/内嵌浏览器/更新资源各自大小；大文件 | 先列具体缓存与日志候选，再列附件画像与DB保留理由。不要只说“全部去App里清理”，也不要把 Caches/Files 全视为可再生。 |
| 浏览器 `cefcache` 等 | `Cache`、`Code Cache` 与 IndexedDB/Local Storage/Service Worker 分开；占用进程 | 具体网页缓存可再生；整个 cefcache 可能包括站点与离线应用数据，不能按总量标绿。 |
| `Publishsys/pkg/*/tmp/*.zip` | ZIP 成员名样本、版本目录是否已解压、文件日期/是否正在更新 | 样本可说明是网页功能资源/应用市场/公共模块，不能推出全部仅“非聊天功能”。临时ZIP与当前解压资源分开，保留所需版本；不用功能也可能自动预下载。 |
| 日志、回收站、附件 | 日志而非数据库；文件大小/类型/日期；回收站内实际文件；云盘同步语义 | 日志清理丢诊断信息；云盘内部Trash不等于macOS废纸篓，优先应用管理，不能不查同步行为就手删。用户确认的本地具体文件可按授权处置。 |

识别卸载残留、旧账户、共用组件、图库或长期未更新的功能目录时，继续读 [卸载残留与时间判断](app-residuals.md)，包括首次报告的候选筛查、归属证据阶梯和mtime判断。

## 完整度验收

首次报告应能回答：
- 目录里主要是哪几类内容，具体工具/包叫什么，有哪些大文件？
- 每类什么可以动、什么保留，为什么？运行/归属证据到哪一步，未知是什么？
- 推荐处理的**精确路径**是什么，多少是占用、多少是预计可回收？
- 要退出什么，清理后功能/历史/离线能力有什么影响，如何恢复？

默认优先解释体量大的项，也覆盖用户特别关心的目录。深查花费有上限：完成可操作判断就停；遇权限/超时记录为部分，继续独立可查项。不能为追求“100%覆盖”无止境扫描，更不能隐藏缺口。
